Documentation/Guides

Le provider

DnDProvider gère chaque glissement sous lui. Il trouve la cible, démarre les glissements, fait défiler, et informe useDnD et useDnDMonitor de tout ce qui se passe.

Modifier cette page

La page anglaise a changé depuis cette traduction. L'original est à jour. Lire l'original en anglais

Un seul provider pour l'application

App.vue
<script setup lang="ts">
import { DnDProvider } from '@vue-dnd-kit/core';
</script>

<template>
  <DnDProvider>
    <RouterView />
  </DnDProvider>
</template>

Placez un DnDProvider tout en haut, dans App.vue ou un layout, et n'y pensez plus. Chaque composable (makeSortableList, makeDraggable, useDnD…) cherche le provider le plus proche au-dessus du composant dans lequel il s'exécute.

Un composable doit s'exécuter dans un composant rendu à l'intérieur du provider. L'appeler dans le composant dont le propre template contient <DnDProvider> lève No <DnDProvider> found above this component : l'inject de Vue ne voit que les ancêtres.

Ce qu'il gère

PartieCe que fait le provider
EntréesTransforme les entrées au pointeur, tactiles et au clavier en glissements (sensors, activation), un glissement à la fois.
Recherche de la cibleTeste les collisions avec les cibles de dépôt sous le glissement (collision) et les en informe.
L'overlayRend la boîte qui suit le pointeur, téléportée dans body, et la fait atterrir au dépôt.
La sélectionUn seul ensemble d'ids sélectionnés, partagé par toutes les listes et tous les éléments déplaçables sous lui.
Défilement automatiqueFait défiler les conteneurs et la fenêtre quand un glissement approche de leurs bords.
La région liveAnnonce aux lecteurs d'écran les saisies, déplacements, dépôts et annulations.

Il ne rend rien d'autre : votre balisage reste tel quel.

Les options en un coup d'œil

Chaque option a une valeur par défaut qui fonctionne, le provider n'en reçoit donc généralement aucune. Le provider lit ses props au moment où il en a besoin : les démos ci-dessous changent collision, activation et autoScroll en direct.

La liste complète, avec toutes les formes, se trouve dans l'API de DnDProvider. Le provider émet aussi drag-start, drag-move, drag-over, drag-end, drag-cancel et drag-settle, les mêmes événements que ceux qu'entend useDnDMonitor.

useDnD() renvoie le glissement sous forme d'état réactif, dans n'importe quel composant sous le provider :

import { useDnD } from '@vue-dnd-kit/core';

const { status, active, over, pointer, activation, isAutoScrolling, selection, cancel } = useDnD();
ChampCe qu'il contient
status'idle', 'activating' (un appui qui attend son activation), 'dragging', 'dropping' (aucun glissement en cours, mais un overlay atterrit encore, ou un onBeforeDrop asynchrone décide), 'selecting' (un rectangle de sélection).
activeCe qui est glissé : id, ids (tous les ids glissés, en commençant par celui qui a été saisi), items, data, type, element, rect, sensor. null au repos.
overLa cible sous le glissement : id, data, element, rect et accepted. null au-dessus de rien.
pointerLe pointeur en coordonnées du viewport, après les modificateurs.
activation.progressDe 0 à 1 pendant qu'un appui attend son activation : dessinez un anneau avec.
isAutoScrollingLe défilement automatique fait défiler quelque chose.
selectionLa sélection du provider : ids, has, add, delete, toggle, set, clear. Voir le multi-drag.
cancel()Annule le glissement en cours (les items reviennent à leur place), un appui en attente ou un rectangle de sélection.
DropHint.vue
<script setup lang="ts">
import { computed } from 'vue';
import { useDnD } from '@vue-dnd-kit/core';

const { status, over } = useDnD();
const refused = computed(() => status.value === 'dragging' && over.value?.accepted === false);
</script>

<template>
  <p v-if="refused" role="status">This list doesn't take that.</p>
</template>

Dès qu'un dépôt est décidé, active, over et pointer valent null, même pendant que l'overlay atterrit encore (status vaut 'dropping'). Une UI dérivée de ces valeurs n'affiche jamais l'ancien glissement à côté des nouvelles données. Pendant qu'un onBeforeDrop asynchrone attend, l'état reste tel qu'il était au relâchement.

Le glissement suivant n'attend pas la fin d'un atterrissage : il démarre aussitôt, et status vaut 'dragging' pendant que le dernier overlay atterrit autour de lui. Un appui sur un overlay en train d'atterrir le rattrape en plein vol : le glissement reprend là où se trouve l'overlay. onDragSettle indique quand l'overlay d'un glissement est arrivé à destination.

Écouter chaque glissement : useDnDMonitor()

import { useDnDMonitor } from '@vue-dnd-kit/core';

useDnDMonitor({
  onDragStart: ({ active }) => {},
  onDragMove: ({ pointer, delta }) => {},
  onDragOver: ({ over }) => {},                  // the target changed
  onBeforeDrop: (e) => 'accept',                 // or 'reject', 'continue', some ids; may be async
  onDragEnd: ({ active, over, dropped, accepted, position }) => {},
  onDragCancel: ({ active }) => {},
  onDragResume: ({ active }) => {},              // onBeforeDrop answered 'continue'
  onDragSettle: ({ active, over }) => {},        // its overlay has landed
});

Un moniteur entend chaque glissement sous son provider, où qu'il commence : le panneau ci-dessus journalise les glissements de la liste sans l'importer. Il s'arrête quand le composant qui l'a appelé est démonté.

ÉvénementQuand
onDragStartUn glissement commence.
onDragMoveLe glissement bouge.
onDragOverLa cible sous le glissement change.
onBeforeDropLe glissement est relâché. Sa réponse décide du dépôt : voir les décisions de dépôt.
onDragEndLe dépôt a abouti. Les listes triables ont déjà exécuté leur onDrop et écrit le nouvel ordre. dropped vaut false quand le glissement s'est terminé au-dessus d'aucune cible.
onDragCancelEscape, un dépôt sur une cible qui le refuse, ou un onBeforeDrop qui a répondu 'reject'.
onDragResumeonBeforeDrop a répondu 'continue' : rien n'a été déposé, et le glissement continue.
onDragSettleL'overlay du glissement a atterri (ou est revenu à sa place, ou a été rattrapé par le glissement suivant), avec l'événement qu'a reçu onDragEnd ou onDragCancel. D'autres glissements ont pu démarrer entre-temps.

Chaque événement transporte active, over, pointer, delta (le décalage depuis le début), position (où se trouve la boîte glissée dans over, voir glisser-déposer) et, pour les items d'une liste triable, source. Les formes complètes se trouvent dans l'API des événements.

onDragEnd est l'endroit pour le travail « après le dépôt » : sauvegarde, effacement de la sélection, analytics. Le onDrop propre à une liste s'exécute avant son écriture, il voit donc encore l'ancien ordre.

<script setup lang="ts">
import { computed, ref, shallowRef } from 'vue';
import {
  DnDProvider,
  closestCenter,
  closestCorners,
  pointerFirst,
  pointerWithin,
  rectIntersection,
  type CollisionDetection,
  type DnDEndEvent,
  type Key,
} from '@vue-dnd-kit/core';
import Desk from './Desk.vue';
import { magnet } from './magnet';

const DETECTORS: Record<string, CollisionDetection> = {
  pointerFirst,
  pointerWithin,
  rectIntersection,
  closestCenter,
  closestCorners,
  magnet,
};
const names = Object.keys(DETECTORS);
const mode = ref('pointerFirst');

// The ranking of the current frame, best first: a wrapper around the chosen function
// records it, so the targets can show their rank.
const ranked = shallowRef<Key[]>([]);
const collision = computed<CollisionDetection>(() => {
  const detect = DETECTORS[mode.value]!;
  return (args) => (ranked.value = detect(args));
});

const result = ref('Drag the pin or the card over the targets');
const onEnd = ({ over }: DnDEndEvent) => {
  ranked.value = [];
  result.value = over ? `Dropped on ${over.id}` : 'Dropped on nothing';
};
const onCancel = () => {
  ranked.value = [];
  result.value = 'Cancelled';
};
</script>

<template>

          <input v-model="mode" type="radio" :value="name" />
          {{ name }}
        </label>
      </div>

      <Desk :ranked="ranked" />
      <p class="result" aria-live="polite">{{ result }}</p>
    </div>
  </DnDProvider>
</template>

À chaque frame d'un glissement, le provider donne à collision les cibles de dépôt en jeu, et elle renvoie leurs ids, la meilleure en premier. Cinq fonctions sont fournies avec la bibliothèque :

FonctionClasseIdéale pour
pointerFirstCe qui est sous le pointeur ; quand il n'y a rien, ce que chevauche la boîte glissée.La valeur par défaut : précise sous le pointeur, tolérante dans les interstices.
pointerWithinUniquement ce qui est sous le pointeur, la plus intérieure en premier.Des cibles précises : un interstice ne dépose nulle part.
rectIntersectionChaque cible que chevauche la boîte glissée : la priority la plus haute, puis l'imbrication la plus profonde, puis le plus grand chevauchement.De gros items au-dessus de petites cibles, quand le pointeur est au bord de l'item.
closestCenterChaque cible, selon la distance entre le centre de la boîte et le leur.Quelque chose gagne toujours, même de loin : grilles et listes d'items de même taille.
closestCornersChaque cible, selon les distances entre les quatre coins.Des colonnes côte à côte (kanban), des cibles de hauteurs très différentes.

Sous le pointeur, le test de collision respecte ce que voit l'utilisateur : parmi des cibles superposées, seule celle du dessus est touchée (front, jamais back là où elles se chevauchent), et parmi des cibles imbriquées, la plus intérieure vient en premier (subfolder, puis folder).

Votre propre fonction

magnet.ts
import type { CollisionDetection, Coordinates, Rect } from '@vue-dnd-kit/core';

/** How far the point is from the rect: 0 inside it. */
const gap = (rect: Rect, point: Coordinates) =>
  Math.hypot(
    Math.max(rect.left - point.x, 0, point.x - rect.right),
    Math.max(rect.top - point.y, 0, point.y - rect.bottom),
  );

/** What is under the pointer; in a gap, the nearest target within 40px. */
export const magnet: CollisionDetection = ({ hits, pointer, candidates }) => {
  if (hits.length) return hits;
  return candidates
    .filter((candidate) => gap(candidate.rect, pointer) <= 40)
    .sort((a, b) => gap(a.rect, pointer) - gap(b.rect, pointer))
    .map((candidate) => candidate.id);
};
ArgumentCe qu'il contient
pointerLe pointeur, après les modificateurs.
overlayRectLa boîte glissée telle qu'elle est affichée, null sans overlay.
candidatesChaque cible en jeu : id, rect (sa partie visible, rognée par les conteneurs défilants), priority, depth (0 au sommet, plus profond quand elle est imbriquée).
hitsLes cibles sous le pointeur, issues du test de collision, la meilleure en premier.

Renvoyez un tableau vide pour « aucune cible ». Les cibles désactivées, les cibles à l'intérieur des items glissés et les cibles masquées par leurs conteneurs défilants n'atteignent jamais la fonction. Une cible qui refuse le glissement reste en compétition : au-dessus d'elle, over.accepted vaut false et un dépôt est refusé (une cible à l'intérieur d'un item triable s'efface plutôt, pour que la liste se trie au-dessus d'elle). La démo enveloppe la fonction choisie pour enregistrer son classement : (args) => (ranked.value = detect(args)).

Le provider amortit les changements que demande la fonction. Une cible que le glissement vient de quitter ne peut pas regagner avant que le pointeur ait bougé de 10 px, pour que les frontières ne clignotent pas. Entre les cibles imbriquées dans un parent (les interstices d'une colonne de cartes), la dernière cible reste.

Quand un appui devient un glissement

Un appui ne glisse pas tout de suite. activation règle, pour chaque type de pointeur (mouse, touch, pen), ce qu'il attend : une distance en px, un delay en ms (avec une tolerance au-delà de laquelle l'appui abandonne, pour que la page puisse défiler), ou la première des deux.

<DnDProvider :activation="{ mouse: { distance: 8 }, touch: { delay: 300, tolerance: 8 } }">
PointeurPar défaut
mouse, pen{ distance: 4 } : un clic reste un clic. Un appui de souris sur une poignée (handle) démarre tout de suite, et reste un clic s'il ne bouge pas.
touch{ delay: 200, tolerance: 5 } : un appui long, pour que les listes continuent de défiler sous le doigt.

Un type que vous omettez garde sa valeur par défaut. L'activation propre à un élément déplaçable l'emporte sur celle d'une zone de glissement, qui l'emporte sur celle du provider. Pendant qu'un appui attend, useDnD().status vaut 'activating' et activation.progress va de 0 à 1 ; Escape ou useDnD().cancel() l'abandonne. Essayez les contraintes en direct, et dessinez un anneau d'appui long à partir de la progression, dans les capteurs.

Tout élément avec overflow: auto ou scroll défile tout seul, et la fenêtre aussi. Le provider fait d'abord défiler le conteneur sous le pointeur, puis ses ancêtres, puis la fenêtre.

OptionPar défautCe qu'elle règle
threshold0.2La zone de bord, en fraction de la taille du conteneur, entre 24 et 96 px.
acceleration10La vitesse tout au bord, en px par frame. Elle croît avec le carré de la profondeur dans la zone : le départ est donc lent et précis.
maxSpeed25La vitesse maximale. Au-delà du bord (le pointeur hors du conteneur), la vitesse continue de croître jusqu'à elle.

:auto-scroll="false" le désactive. Une direction ne défile qu'une fois que le pointeur a bougé dans ce sens : un item saisi près d'un bord ne défile donc pas tout seul. Les listes, les arbres et les zones de glissement prennent leur propre autoScroll pour leur conteneur :

makeSortableList(list, { items: channels, autoScroll: { maxSpeed: 10 } });

Les glissements au clavier ne déclenchent jamais le défilement automatique : ils font défiler l'item pour le rendre visible. isAutoScrolling (de useDnD(), ou d'une zone de glissement) vaut true pendant que quelque chose défile.

Vibrations et touche de copie

Un glissement tactile vibre brièvement quand il commence. :haptics="false" le désactive ; un objet règle chaque vibration :

<DnDProvider :haptics="{ start: true, enter: 10, drop: 10, refuse: [20, 40, 20] }">
CléVibre quandPar défaut
startL'appui long devient un glissement.true (10 ms)
enterLe glissement entre dans une cible qui l'accepte.désactivé
dropLe dépôt aboutit.désactivé
refuseLe dépôt est refusé et les items reviennent à leur place.désactivé

Chacune prend true (le motif par défaut), une durée en ms, un motif marche/arrêt, ou false. Seuls les glissements commencés au toucher vibrent, et Safari sur iOS ne peut pas vibrer du tout.

copyModifier est la touche qui, maintenue pendant un glissement entre des listes, transforme le déplacement en copie : 'Alt' par défaut, n'importe quelle KeyboardEvent.key, ou null pour aucune. La liste d'où viennent les items a besoin d'une fonction clone ; voir les listes qui partagent des items.

Plusieurs providers

La plupart des applications en ont besoin d'un seul. Placez la liste de souhaits sous son propre provider, puis essayez d'y déplacer un livre : il ne peut pas quitter son provider, et le moniteur extérieur n'entend plus la liste de souhaits.

  • Les providers sont indépendants : un glissement ne passe jamais de l'un à l'autre.
  • Les providers imbriqués sont autorisés. Le propriétaire le plus proche l'emporte : un item appartient au provider le plus proche au-dessus de lui, et le provider extérieur l'ignore.
  • Chaque provider a sa propre sélection, son propre overlay, sa propre région live et ses propres moniteurs.

Un second provider n'a de sens que pour une partie de la page qui a besoin de ses propres réglages à l'échelle du provider (collision, touches du clavier, annonces) et dont les items n'en sortent jamais. Si des items ne peuvent pas passer d'une partie de votre page à une autre, vérifiez qu'ils ne se trouvent pas sous deux providers.

Des règles pour une partie de la page (un tableau qui s'aligne sur une grille, un fil avec un appui tactile plus long, un panneau où rien ne glisse) ne nécessitent pas leur propre provider :
makeDragArea(board, { modifiers: [snapToGrid(20)], activation: { touch: { delay: 400 } } });
Ses items restent dans le provider de l'application et peuvent toujours aller n'importe où. Voir les contraintes.

Une application montée ailleurs, dans un shadow root ou comme application Vue séparée, peut rejoindre un provider existant : passez useDnDContext() à provideDnDContext(app, context) avant de la monter. Le test de collision et l'overlay fonctionnent à travers les shadow roots.

SSR et Nuxt

Le provider est compatible SSR. Les listes et les items sont rendus sur le serveur comme n'importe quel autre balisage. L'overlay et la région live sont téléportés et se montent uniquement côté client : ils ne provoquent donc jamais d'erreur d'hydratation. Les ids par défaut viennent du useId() de Vue et sont identiques sur le serveur et le client.

Dans Nuxt, le module enregistre DnDProvider globalement et importe automatiquement les composables : voir l'installation.
