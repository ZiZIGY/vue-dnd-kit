A sensor turns input into drags. It only tells the provider "drag this item from here", then where
the input moved, and whether it dropped or cancelled. The provider does the rest, the same way for
every sensor: one drag at a time, disabled items refused, activation constraints, sorting,
auto-scroll, announcements, :kbd{value="Escape"} and the whole drop.

## The built-in sensors

| Sensor | Input |
| --- | --- |
| `pointerSensor` | Mouse, touch and pen, through Pointer Events. It captures the pointer, keeps the page from selecting text or scrolling under a touch drag, and swallows the click that follows a drag. |
| `keyboardSensor` | :kbd{value="Space"} and :kbd{value="Enter"} pick up and drop, arrows move, :kbd{value="Escape"} cancels — any drag, pointer drags too. |

Both run by default. The provider's `sensors` replaces the list:

```vue
<script setup lang="ts">
import { DnDProvider, keyboardSensor, pointerSensor } from '@vue-dnd-kit/core';
import { joystick } from './joystick';
</script>

<template>
  <DnDProvider :sensors="[pointerSensor, keyboardSensor, joystick.sensor]">
    <App />
  </DnDProvider>
</template>
```

To turn keyboard drags off, prefer `:keyboard="false"` to leaving `keyboardSensor` out: the
keyboard sensor is also what cancels any drag with :kbd{value="Escape"}. Its keys are rebound with
`keyboard.keys` (see [Accessibility](/docs/guides/accessibility#the-keyboard)).

## Activation constraints

A press becomes a drag once it meets its constraint:

| Pointer | Default |
| --- | --- |
| Mouse | After moving 4 px. At once when pressed on a `handle`, unless you set a constraint for the mouse. |
| Pen | After moving 4 px. |
| Touch | After a 200 ms press. Moving more than 5 px first aborts it, so the page scrolls instead. |

A constraint has three fields:

| Field | Meaning |
| --- | --- |
| `distance` | Pixels the pointer must travel. |
| `delay` | Milliseconds the press must last. With both, whichever comes first starts the drag. |
| `tolerance` | With `delay`: how far the pointer may move meanwhile; past it the press is abandoned. |

Set them per pointer kind — `mouse`, `touch`, `pen` — on the provider, a drag area or the item
itself. The item's own wins, then its area's, then the provider's:

```ts
makeSortableItem(el, { item: () => props.task, activation: { touch: { delay: 300, tolerance: 8 } } });
```

```vue
<DnDProvider :activation="{ mouse: { distance: 8 }, touch: { delay: 250, tolerance: 5 } }">
```

To drag at once by touch from a handle, give the handle `touch-action: none` (so the browser
doesn't scroll) and the item `activation: { touch: { distance: 4 } }`.

### A long-press ring

While a press waits, `useDnD().status` is `'activating'` and `activation.progress` goes from 0 to 1:

```vue [PressRing.vue]
<script setup lang="ts">
import { useDnD } from '@vue-dnd-kit/core';

const { status, activation: { progress } } = useDnD();
</script>

<template>
  <svg v-if="status === 'activating'" class="ring" viewBox="0 0 36 36">
    <circle cx="18" cy="18" r="16" pathLength="1" :stroke-dasharray="`${progress} 1`" />
  </svg>
</template>
```

### Only some presses

`canDrag` is one more gate on draggables and sortable items. It gets the input event:

```ts
// Pointer drags only while Alt is held; keyboard drags as usual.
makeDraggable(el, { canDrag: (event) => event instanceof KeyboardEvent || event.altKey });
```

Interactive children — buttons, inputs, editable fields — never start a pointer drag, so they keep
working inside a draggable. With a `handle`, only the handle starts one.

## A sensor of your own

A gamepad, an on-screen joystick, voice commands: anything that can point at an item and move can
drive a drag. Here is a joystick that picks up what is under its cursor after a 300 ms hold:

```ts [joystick.ts]
import { shallowRef } from 'vue';
import { defineSensor, type Coordinates, type SensorContext, type SensorDrag } from '@vue-dnd-kit/core';

export function createJoystick() {
  const cursor = shallowRef<Coordinates>({ x: 0, y: 0 });
  let context: SensorContext | null = null;
  let drag: SensorDrag | null = null;

  const sensor = defineSensor({
    name: 'joystick', // shows in the DevTools log
    // Runs once per provider, in the browser, in an effect scope: VueUse listeners made
    // here are removed with it. Return a cleanup if you need one.
    setup(ctx) {
      context = ctx;
      return () => {
        context = null;
        drag = null;
      };
    },
  });

  /** "A": drops a running drag, or picks up what is under the cursor after a hold. */
  const press = () => {
    if (drag?.state === 'dragging') return void drag.drop();
    const target = document.elementFromPoint(cursor.value.x, cursor.value.y);
    if (!target || !context) return;
    drag = context.activate({
      target, // an element inside a draggable, or a draggable's id
      point: cursor.value, // where the drag starts, in viewport coordinates
      activation: { delay: 300 }, // or 'mouse' | 'touch' | 'pen' for the configured one
      type: 'pointer', // follows points; 'keyboard' moves by items
      onEnd: (ended) => {
        if (drag === ended) drag = null;
      },
      // onBeforeDrop answered 'continue': the drag goes on, and its calls apply again.
      onResume: (resumed) => {
        drag = resumed;
      },
    }); // null: refused (another drag runs, the item is disabled, a button inside it…)
  };

  const move = (dx: number, dy: number) => {
    cursor.value = { x: cursor.value.x + dx, y: cursor.value.y + dy };
    drag?.move(cursor.value); // pending: checks the tolerance; dragging: moves
  };

  const cancel = () => drag?.cancel();

  return { sensor, cursor, press, move, cancel };
}

export const joystick = createJoystick();
```

Add it to the provider's `sensors`, or run it for as long as a component lives with
`useSensor(joystick.sensor)`.

### What the sensor gets

`setup(context)` receives the provider's side:

| Member | What it is |
| --- | --- |
| `props` | The provider's props (`activation`, `keyboard`…). Read them when needed: they may change. |
| `status` | The provider's drag status, whichever sensor runs the drag. |
| `drag` | The provider's current drag, pending or running, whichever sensor started it. `null` when there is none. |
| `activate(options)` | Asks for a drag. Returns a `SensorDrag`, or `null` when no drag may start. |
| `cancel()` | Cancels the provider's drag or pending press. |

`activate()` takes:

| Option | Meaning |
| --- | --- |
| `target` | Where the input landed: an element inside a draggable, or a draggable's id. An element is checked like a real press (handle, no interactive child); an id skips the checks. |
| `point` | Where the drag starts, in viewport coordinates. Default: the center of the draggable. |
| `type` | `'pointer'` (default): follows points, hit-tests targets, auto-scrolls. `'keyboard'`: moves by items, reveals targets, returns focus at the end. |
| `activation` | A constraint (`{ delay: 300 }`), or a pointer kind (`'touch'`) to use the configured one. Default: none, the drag starts at once. |
| `event` | The input event, handed to the item's `canDrag`. A touch `pointerType` makes it a touch drag (haptics). |
| `onStart(drag)` | The drag started, after its activation. |
| `onEnd(drag)` | The drag is over: aborted, dropped or cancelled — by anyone. |
| `onResume(drag)` | `onBeforeDrop` answered `'continue'`: the drag goes on, and `move`, `drop` and `cancel` apply again. |

The `SensorDrag` it returns:

| Member | What it does |
| --- | --- |
| `id`, `type` | The dragged item's id, and `'pointer'` or `'keyboard'`. |
| `state` | `'pending'` (waiting for the activation), `'dragging'`, then `'ended'`. |
| `started` | The drag started, even if it has ended since. |
| `move(point)` | The input moved. While pending, checks the tolerance; while dragging, moves the drag. |
| `step(direction)` | Keyboard drags: one arrow step, `'up' \| 'down' \| 'left' \| 'right'`. |
| `place({ list, index })` | Puts the item at a position of a sortable list, as keyboard moves do. Resolves `false` when no list takes it there. |
| `drop()` | Drops. Resolves `true` when the drop went through, once it has landed. |
| `cancel()` | Cancels: the item flies back, or a pending press is abandoned. |

Calls that no longer apply — a move after the end, a second `drop()` — are ignored. Full types:
[Sensors](/docs/api/sensors).

::tip
To wrap a built-in sensor, run its `setup` with a context of your own. Make it with
`Object.create(context, { activate: { value: myActivate } })` rather than a spread, so the live
getters (`status`, `drag`, `props`) keep working.
::

## Programmatic drags

`@vue-dnd-kit/actions` moves items from code: "Move up" buttons, menus, keyboard shortcuts, undo,
onboarding tours, tests. It is built on the public sensor API, and its drags are real ones:
announced and animated, through `onBeforeDrop`, `onDrop`, `e.result` and `preventDefault()`, under
the provider's rules (one drag at a time, disabled items, `accept` and `group.put`).

```bash
npm i @vue-dnd-kit/actions
```

### moveItem: one call, one move

```ts
import { useDnDActions } from '@vue-dnd-kit/actions';

const { moveItem } = useDnDActions(); // in setup, under a provider

await moveItem('card-1', { index: 0 }); // to the top of its list
await moveItem('card-1', { list: 'done' }); // to the end of another list
await moveItem('card-1', { list: 'done', index: 2 }); // to a place in another list
```

- `list` is a sortable list's `id`. Without it, the item stays in its list.
- `index` is where the item ends up, counted without the item itself, and clamped to the list.
  Without it, the item goes to the end.
- It resolves `true` when the drop went through, `false` when the item isn't rendered or is
  disabled, no list takes it there, or the drop was refused.
- Calls queue: each waits until the provider is idle, so a quick second click isn't lost.
- It runs as a keyboard drag, so it is announced and the focus stays on the item.
- Lists only: tree positions also have a depth.

See [Accessibility](/docs/guides/accessibility#moving-without-dragging) for a row with move buttons.

### startDrag: a scripted drag

```ts
const { startDrag } = useDnDActions();

const drag = startDrag('card-1'); // null when it can't start now
if (drag) {
  await drag.moveTo(document.querySelector('#trash')!); // onto an element
  await drag.moveTo({ x: 400, y: 120 }); // to a point, in viewport coordinates
  await drag.moveTo({ list: 'done', index: 2 }); // to a list position
  await drag.drop(); // true when the drop went through; or drag.cancel()
}
```

`moveTo` resolves once the move has rendered, `drop` once the drop has landed. `startDrag(id, { type:
'keyboard' })` moves by items instead (`await drag.step('down')`), and the keyboard sensor can take
over: a "Move" menu item that hands the item to the arrow keys.

### Outside components

`useDnDActions()` runs one sensor, named `actions`, in the provider above. To drive a provider from
a store or a test harness, or under a name of your own, create the actions in a sensor you run
yourself:

```ts
import { defineSensor } from '@vue-dnd-kit/core';
import { createDnDActions, type DnDActions } from '@vue-dnd-kit/actions';

export let tour: DnDActions | undefined;
export const tourSensor = defineSensor({
  name: 'tour',
  setup: (context) => void (tour = createDnDActions(context)),
});
```

```vue
<DnDProvider :sensors="[pointerSensor, keyboardSensor, tourSensor]">
```

Then `await tour?.moveItem('card-1', { list: 'done' })` from anywhere. During server rendering
nothing drags: `moveItem` resolves `false` and `startDrag` returns `null`.
