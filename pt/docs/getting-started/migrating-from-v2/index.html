Migrando da v2

Leve um app da v2 para a v3 — o que mudou e por quê, a atualização, um mapa de cada API da v2 para a substituta na v3, código antes e depois para os casos comuns, e as armadilhas.

Esta página foi traduzida por IA e pode conter imprecisões. Ler o original em inglês

A v3 é uma reescrita da v2. O modelo continua: um provider, e composables que você chama nos seus próprios elementos. Mas a maioria dos nomes e das opções mudou, a ordenação passou para dentro da biblioteca, e o handler de drop que você escrevia para cada lista vai embora. Esta página mapeia cada parte da v2 para a v3 e depois mostra os casos comuns antes e depois.

O que mudou

  • A ordenação vem embutida. Na v2, uma lista era uma zona de drop, as linhas dela eram draggables com um payload [index, items], e você ordenava no onDrop com e.helpers.suggestSort(). Na v3, makeSortableList e makeSortableItem fazem isso: a lista renderiza um rascunho do seu array que se reordena enquanto você arrasta, e o drop grava o novo array no seu ref. A maioria dos handlers de drop da v2 é apagada, não portada.
  • As coisas se movem sozinhas. As linhas deslizam para os novos lugares (FLIP), o overlay pousa na sua posição no drop e volta ao lugar no cancelamento. O <TransitionGroup> vai embora.
  • Continua um pacote só. @vue-dnd-kit/core contém listas, árvores, multi-drag, modificadores, sensores e as funções de colisão. O módulo do Nuxt continua; @vue-dnd-kit/actions (arrastes programáticos) e @vue-dnd-kit/devtools são novos e opcionais.
  • Um overlay de verdade. Ele é teleportado para o body e mostra um clone profundo, do tamanho da posição onde vai pousar. Componentes de overlay recebem o arraste como props em vez de ler o funcionamento interno do provider.
  • Ids, não elementos. A seleção, os eventos e o estado do arraste usam como chave ids dos seus dados. Não há mapas de elementos do DOM para ler.
  • Tipos e regras de aceitação substituem groups para draggables simples e alvos. As listas trocam itens pelo nome do group.
  • Decisões antes do drop. onBeforeDrop aceita, recusa, mantém o arraste em andamento ou fica com parte dos itens. onDrop só aplica.
  • Sensores. A entrada de ponteiro e a de teclado são sensores. A ativação é definida por tipo de ponteiro, e os arrastes por toque começam com um toque longo, então as listas continuam rolando sob o dedo.
  • Áreas. makeDragArea substitui makeConstraintArea e makeAutoScroll, e a rolagem automática funciona em todo contêiner com rolagem, sem código.
  • A acessibilidade vem ligada por padrão: atributos ARIA, o foco que volta depois do drop e anúncios para leitores de tela.

  • Um app que tem "@vue-dnd-kit/core": "^2…" no package.json fica na v2 até a faixa de versões dizer ^3.
  • Vue 3.5 ou mais novo. A v2 não tinha dependências; a v3 tem uma, @vueuse/core (14 ou 15).
  • Navegadores: Chrome e Edge 104+, Safari 15.4+, Firefox 104+.
  • A v2 e a v3 compartilham o nome do pacote, então um app passa para a v3 de uma vez. Não há camada de compatibilidade. A documentação da v2 continua disponível no menu de versões no topo da página.

Uma boa ordem de trabalho:

  1. Atualize os pacotes e renomeie as props do provider (abaixo).
  2. Transforme cada lista ordenável em makeSortableList e makeSortableItem, e apague o handler de drop dela.
  3. Porte os draggables simples e as zonas de drop.
  4. Porte as prévias personalizadas para componentes de overlay ou para o slot #overlay do provider.
  5. Substitua makeConstraintArea e makeAutoScroll por makeDragArea, ou por nada.
  6. Apague os contornos da v2: tabindex e aria-grabbed nos draggables, touch-action: none em itens inteiros, <TransitionGroup> em volta das linhas, markRaw em volta dos componentes de prévia.

Um onDrop da v2 podia retornar um valor, ou uma promise de um valor, para decidir o drop. Na v3 esse é o papel do onBeforeDrop, em listas, árvores, alvos de drop e monitores:

O onDrop da v2 retornaO onBeforeDrop da v3 retorna
Nada, ou true: o drop é concluído'accept', true ou nada.
false: este drop é descartado, o arraste continua ativo'continue'. false agora recusa o drop.
Uma promise rejeitada, ou um throw: o arraste é cancelado'reject' ou false. Um throw também rejeita.
Uma promise; enquanto isso state é 'pending'Uma promise; enquanto isso status é 'dropping' e o overlay espera com data-dnd-overlay="dropping".
onValidate retorna IDragItem[]Um array de ids: só esses são soltos, os outros voltam ao lugar.

Os monitores respondem primeiro, depois o alvo. Então o onDrop do alvo roda, uma lista grava os novos arrays, e o onDragEnd vem em seguida. Mais em decidindo um drop e na API de eventos.

Uma lista ordenável

v2

TaskList.vue
<script setup lang="ts">
import { useTemplateRef } from 'vue';
import { makeDroppable, type IDragEvent } from '@vue-dnd-kit/core';
import TaskItem from './TaskItem.vue';

const tasks = defineModel<Task[]>({ required: true });
const el = useTemplateRef<HTMLElement>('el');

makeDroppable(
  el,
  {
    events: {
      onDrop(e: IDragEvent) {
        const r = e.helpers.suggestSort('vertical');
        if (r) tasks.value = r.targetItems as Task[];
      },
    },
  },
  () => tasks.value,
);
</script>

<template>
  <div ref="el">
    <TransitionGroup name="list">
      <TaskItem v-for="(task, index) in tasks" :key="task.id" :task="task" :index="index" :tasks="tasks" />
    </TransitionGroup>
  </div>
</template>

Listas que compartilham itens

v2

Board.vue
// Each column's makeDroppable calls this from its onDrop, with its array as the payload.
function applySort(e: IDragEvent) {
  const r = e.helpers.suggestSort('vertical');
  if (!r) return;

  const src = e.draggedItems[0]?.items;
  const tgt = e.hoveredDraggable?.items ?? e.dropZone?.items;

  if (src === todo.value) todo.value = r.sourceItems as Task[];
  else if (src === done.value) done.value = r.sourceItems as Task[];

  if (!r.sameList) {
    if (tgt === todo.value) todo.value = r.targetItems as Task[];
    else if (tgt === done.value) done.value = r.targetItems as Task[];
  }
}

O drop grava os dois arrays, o que a tarefa deixou e o em que ela entrou. TaskItem.vue é o da lista ordenável acima. Uma paleta que distribui cópias era suggestCopy() e uma flag copyOnly; agora é uma lista:

Palette.vue
makeSortableList(el, {
  items: blocks,
  group: { name: 'board', pull: 'clone', put: false },  // copies go out, nothing comes in
  sort: false,                                          // its own order stays
  clone: (block) => ({ ...block, id: crypto.randomUUID() }),
});

Para um store Pinia ou outro estado que você não grava diretamente, passe items como getter, chame e.preventDefault() no onDrop e aplique e.result: veja listas controladas.

Um drop que você confirma

v2

Zone.vue
makeDroppable(el, {
  events: {
    onDrop: (e) =>
      new Promise<void | boolean>((resolve) => {
        if (!window.confirm('Drop here?')) return resolve(false); // keep dragging
        place(e.draggedItems);
        resolve();
      }),
  },
});

v3

Zone.vue
makeDroppable(el, {
  onBeforeDrop: () => (window.confirm('Drop here?') ? 'accept' : 'continue'),
  onDrop: (e) => place(e.active.items),
});

Uma lista pergunta do mesmo jeito, e uma promise permite abrir um diálogo seu. O overlay espera onde foi solto até a promise terminar:

Column.vue
makeSortableList(el, {
  items: toRef(props.column, 'tasks'),
  group: 'board',
  // `ask` opens a dialog and resolves 'accept', 'continue' or 'reject'.
  onBeforeDrop: (e) => (e.sameList ? 'accept' : ask(e)),
});

Zone.vue
import type { DragItem } from '@vue-dnd-kit/core';

const fits = (item: DragItem) => item.type.length === 0 || item.type.includes('frontend');

makeDroppable(el, {
  accept: 'frontend',
  acceptMode: 'some',
  onBeforeDrop: (e) => e.active.items.filter(fits).map((item) => item.id), // the others fly back
  onDrop: (e) => place(e.active.items.filter(fits)), // `active.items` still lists every dragged item
});

As listas fazem isso sem código: com acceptMode: 'some', os itens que o group.put delas aceita pousam, e os outros voltam ao lugar.

Armadilhas ao atualizar

  • Instale a v3 com a faixa dela. ^3 no package.json: um npm update mantém ^2 na v2.
  • Renderize o rascunho. Uma lista renderiza os items que makeSortableList retorna, não o seu array. Renderizando o seu array, nada se move até o drop.
  • Não ordene duas vezes. Apague o código de suggestSort das listas: uma lista grava cada drop em um ref items gravável depois do onDrop dela. Para aplicá-lo você mesmo, chame e.preventDefault() e use e.result.
  • false recusa o drop. Na v2, um onDrop que resolvia false mantinha o arraste em andamento. Na v3, retorne 'continue' do onBeforeDrop. Uma promise retornada do onDrop é ignorada.
  • Listas só compartilham dentro de um group. Uma lista sem um não troca itens com nenhuma outra lista.
  • Use ids como key das linhas. :key="index" anima as linhas erradas. Passe ids a partir dos seus dados também: um id padrão é novo a cada instância do componente.
  • Nada de <TransitionGroup>, nada de transition em transform. A biblioteca move as linhas ela mesma, e os movimentos seriam animados duas vezes.
  • Desfaça o contorno para toque. touch-action: none em um item inteiro impede a página de rolar sob o dedo; a v3 começa os arrastes por toque com um toque longo. Mantenha-o em um handle que deve arrastar na hora, com activation: { touch: { distance: 4 } }.
  • Remova atributos obsoletos. A biblioteca define o tabindex, o role e os aria-* de que precisa e nunca sobrescreve os seus, então um role ou um aria-grabbed que sobrou fica como você o deixou.
  • Refaça o estilo do overlay. .dnd-kit-preview não existe mais: estilize o que está dentro de [data-dnd-overlay='dragging'], nunca o transform da caixa. Dê width: 100%; height: 100% à raiz de um componente de overlay, e tire <DragPreview /> dos seus layouts.
  • A rolagem automática está ligada. Passe :auto-scroll="false" onde a v2 nunca rolava.
  • Um retângulo de seleção não precisa de tecla. makeSelectionArea desenha a partir de um simples pressionar no espaço vazio dela. Adicione um modifier para manter o Ctrl da v2.
  • Um provider, áreas dentro dele. Itens não podem passar de um provider para outro. Uma página que usava um provider por região para manter as regras separadas precisa de um provider e de um makeDragArea por região.
  • Dois argumentos. makeDraggable e makeDroppable recebem um ref e um objeto de opções, sem payload.
